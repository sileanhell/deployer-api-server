# deployer-api-server

HTTPS-сервис для деплоя приложений на сервер. CI (например, GitHub Actions) отправляет ZIP-архив, а сервис:

1. проверяет sha256 архива и распаковывает его;
2. останавливает сервис приложения (systemd, OpenRC или runit; init-система определяется сама);
3. удаляет старые файлы, кроме тех, что нужно сохранить (`.env`, данные, логи…);
4. кладёт новые файлы и запускает сервис обратно.

Прогресс можно получать построчно прямо во время деплоя. Несколько деплоев могут идти одновременно; деплои
одного сервиса или одного каталога выстраиваются в очередь.

## Сборка

GitHub Actions ([.github/workflows/build.yml](.github/workflows/build.yml)) на каждый push в `main` проверяет
типы (`bun run typecheck`), затем запускает отдельный job на каждую платформу. Они идут параллельно, собирают
исполняемый файл последней версией Bun и сразу загружают его отдельным артефактом.

| Файл | Платформа |
|---|---|
| `deployer-linux-x64` | Linux x64 (glibc: Debian, Ubuntu) |
| `deployer-linux-x64-musl` | Linux x64 (musl: Alpine, Void musl) |
| `deployer-linux-arm64` | Linux ARM64 (glibc) |
| `deployer-linux-arm64-musl` | Linux ARM64 (musl) |
| `deployer-windows-x64.exe` | Windows x64 |
| `deployer-windows-arm64.exe` | Windows ARM64 |

Для musl-сборок нужны `libstdc++` и `libgcc` (`apk add libstdc++ libgcc`). Локально:

```bash
bun build src/main.ts --compile --minify --target=bun-linux-x64 --outfile dist/deployer-linux-x64
```

Бинарник читает `.env` из текущего каталога, как и `bun src/main.ts`.

## Переменные окружения

Задаются в `.env` рядом с проектом (Bun читает его сам) или в окружении процесса.

| Переменная  | По умолчанию    | Описание                                                                                                                          |
| ----------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `API_KEY`   | **обязательна** | Ключ авторизации, минимум 16 символов.                                                                                            |
| `PORT`      | `8443`          | Порт HTTPS-сервера                                                                                                                |
| `HOST`      | `0.0.0.0`       | Адрес, на котором слушает сервер                                                                                                  |
| `CERT_DIR`  | `./certs`       | Где хранить самоподписной сертификат и ключ                                                                                       |
| `CERT_DAYS` | `3650`          | Срок действия сертификата в днях                                                                                                  |
| `CERT_IPS`  | —               | Дополнительные IP для сертификата через запятую, например внешний IP, если сервер за NAT. IP сетевых интерфейсов добавляются сами |

## Деплой

```
POST https://<IP-сервера>:<PORT>/
```

Тело запроса — сам ZIP-архив (сырые байты, не multipart). `GET /` — проверка, что сервер жив.

### Заголовки

| Заголовок                         | Обязателен | Описание                                                                                                                                     |
| --------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization: Bearer <API_KEY>` | да         | Ключ из `.env`                                                                                                                               |
| `X-Archive-SHA256`                | да         | sha256 архива (hex). Не совпал — `422`, деплой не начинается                                                                                 |
| `X-Deploy-Dir`                    | да         | Абсолютный путь каталога, куда разворачивать: `/opt/my-app`                                                                                  |
| `X-Service-Name`                  | нет        | Сервис для stop/start: `my-app`. Не передан или не найден в системе — шаги stop/start пропускаются                                           |
| `X-Keep-Files`                    | нет        | Что не удалять, glob-паттерны через запятую: `.env,data,logs/*.log,binary.*`. Уже существующие сохраняемые файлы не перезаписываются архивом |
| `Accept: application/x-ndjson`    | нет        | Получать прогресс построчно (см. ниже)                                                                                                       |

### Сертификат

Сертификат самоподписной, создаётся при первом запуске в `CERT_DIR/cert.pem` и выписан на **IP-адреса
сервера**, поэтому обращаться к серверу нужно по IP, а не по домену.

1. Возьмите `certs/cert.pem` с сервера. Это публичный сертификат; `key.pem` никуда не копируйте.
2. Сохраните его в CI, например в секрет `DEPLOY_CERT` в GitHub Actions.
3. Передайте его curl через `--cacert`: тогда curl проверит, что отвечает именно ваш сервер.

Сверить сертификат можно по отпечатку: сервер печатает `[tls] SHA256 fingerprint: ...` при старте.
Если IP сервера сменится, сертификат перевыпустится сам, и `cert.pem` в CI нужно будет обновить.

### Пример

```bash
curl --fail-with-body -sS \
  --cacert cert.pem \
  -H "Authorization: Bearer $API_KEY" \
  -H "X-Archive-SHA256: $(sha256sum app.zip | cut -d' ' -f1)" \
  -H "X-Deploy-Dir: /opt/my-app" \
  -H "X-Service-Name: my-app" \
  -H "X-Keep-Files: .env,data" \
  --data-binary @app.zip \
  https://203.0.113.10:8443/
```

Без `Accept: application/x-ndjson` ответ приходит один раз, в конце: `200` и `{"status":"success",...}`
при успехе, `500` с полями `step` и `error` при ошибке. Для проверки результата хватает `curl --fail-with-body`.

С `Accept: application/x-ndjson` каждая строка ответа — событие `{"step":"stop","message":"..."}`, а последняя —
`{"status":"success"}` или `{"status":"error",...}`. HTTP-код в этом режиме всегда `200`, поэтому успех
определяется по последней строке.

### Коды ответа

`200` готово · `400` неверные заголовки · `401` неверный ключ · `415` неподходящий Content-Type ·
`422` хеш не совпал · `500` ошибка деплоя.
